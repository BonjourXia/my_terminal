从零复现 smart_terminal —— 分阶段手册

这份手册带你从空目录开始，把整个 smart_terminal 完整重新写出来。

主要目的不是"让程序在板子上跑起来"，而是让你学会「从零把一整个嵌入式 Qt 项目复现出来」这套本事。 所以：每一级都完整做，一个都不跳过。

怎么用这份手册

🎯 第一个目标：跑起来，看见黑导航栏

在你写任何功能之前，先把第 1 部分做完 —— 屏幕上出现"左边一条黑色导航栏，右边一片空白"，点导航能切换。

这个画面看起来毫无成就感，但它是整个项目的骨架：后面 7 级做出来的每一个页面，都要挂进这个骨架里。 这一步做完，你才算有了一个"项目"；否则你写的只是一堆散的 .cpp。

章节号和级数差 1：第 1 部分 = 第 0 级（空壳），第 2 部分 = 第 1 级（轮播图），依此类推。

📌 两条贯穿全程的约定

  1. 全程不用 Qt Designer，界面 100% 用 C++ 代码写。 一个 .ui 文件都不建，.pro / .pri 里也不会出现 FORMS。 后果、写法和那个最坑的地方（on_xxx_clicked 会静默失效），动手前先读 §0.5。
  2. 原项目全程只读，不改。 你的代码写进另一个工程 my_terminal/，原项目留着当对照的答案。逐行对照是你最主要的学习手段，所以本手册里凡是提到"照抄原码"，就是指抄这个名字、这个数字、这个结构。

每一级的固定节奏

  1. 写 —— 按 Step 1..N 一步步来，每步都是能编译、能看见结果的最小单元
  2. 验 —— 对照 ✅ 验收标准逐条打勾
  3. 对 —— 打开原文件比一比，看作者怎么写的、你哪里不一样

不要一次写完一个页面再跑 —— 那是调试地狱，不是学习。

0.3 数据文件放哪：applicationDirPath() 是个坑

原项目里到处是这种写法：

QString path = QCoreApplication::applicationDirPath() + "/myMusic";   // 可执行文件所在目录 + "/myMusic"

applicationDirPath() 是可执行文件所在目录，不是源码目录，也不是你敲命令的目录。

这就意味着两件事：

  1. 你在 Qt Creator 里用的是影子构建（shadow build），可执行文件生成在 build-xxx-Debug/ 里。 所以 myMusic/、myVideo/、opencv_src/ 必须拷到那个 build 目录，不是拷到源码目录。
  2. 在板子上运行时，你必须先 cd 到程序所在目录再启动，否则读不到数据 —— 而且列表是空的，还不报错。

这是本手册里出现频率最高的一个坑，第 4、5、6、7 级都会再碰到。

.pri 是干什么的

form/ 里 9 个页面 = 27 个文件。要是全写进 .pro，那个文件会变成一坨。所以作者的解法是目录自治：

# 三个文件的关系（这是示意图，不是要敲的代码）
my_terminal.pro                form/form.pri              hardware/hardware.pri
──────────────────             ─────────────              ─────────────────────
SOURCES += main.cpp            HEADERS += \               HEADERS += \
    mainwidget.cpp                 $$PWD/banna.h \            $$PWD/led.h \
                                       ...                        ...
include(./form/form.pri)   ←── 这一行等价于"把 form.pri 的内容原地粘到这里"
include(./hardware/hardware.pri)  ←── 同理，把 hardware.pri 粘过来
  • include(xxx.pri) 就是把那个文件的内容原地粘贴到这一行。.pri 不是新语法，就是 .pro 的碎片。
  • $$PWD 是 qmake 内置变量 = 这个 .pri 自己所在目录。所以 form.pri 里写 $$PWD/banna.h 等价于 form/banna.h，跟你在哪个目录敲 qmake 无关。
  • 好处：以后加页面只改 form.pri，.pro 永远不用动。

还有一行关键配置

# 把 form/ 加进头文件搜索路径 → 以后写 #include "banna.h" 就行，不用写路径前缀
INCLUDEPATH += $$PWD/form
# 同理，把 hardware/ 也加进去 → #include "led.h" 就行
INCLUDEPATH += $$PWD/hardware

加了这两行，mainwidget.cpp 里就能直接写 #include "banna.h"，不用写 #include "form/banna.h"。 这就是为什么原码里所有 #include 都不带目录前缀 —— 是编译选项在兜着，不是文件真的在同一个目录。

你这遍复现，一个 .ui 都不建，10 个全部用代码搭。 而且要注意：上面那 5 个空壳仍然会拖累你 —— 因为 .ui 一旦登记进 FORMS，uic 就会为它生成一个 Ui::MainWidget 之类的类，你哪怕一行不用，也得在头文件里留个 Ui::xxx *ui;。不建 .ui，这层壳就没必要了。

先说清楚：这不是"绕开难点"，是换一条更难但更值钱的路

.ui 是 XML，程序跑起来之前你看不见它的逻辑；而且你没法"写"它，只能"拖"它 —— 拖出来的东西，你并不知道它背后发生了什么。作者自己放着 5 个页面不用 Designer 而手写，恰恰说明他也知道手写才是"真的在写程序"。

代价是：你的代码会跟原码长得不一样，逐行对照时要花点心思（下面有对照表）。这个交换是划算的 —— 你会真正知道每个 setGeometry 是谁调的。

不要写 FORMS +=

.ui 文件在 qmake 里靠 FORMS += 登记，uic 工具把它编译成 ui_xxx.h。既然没有 .ui，就一个 FORMS 都不要写 —— .pro 和 form.pri 里都不写。

写了的后果（我实测过）：

# 这是报错原文（不是要敲的代码）：.pro 里写了 FORMS += mainwidget.ui，但文件不存在
make: *** 没有规则可制作目标"mainwidget.ui"，由"ui_mainwidget.h" 需求。 停止。

所以 form.pri 只有两段：HEADERS 和 SOURCES。 只有零件那个 hardware.pri 本来就只有两段 —— 现在两个文件结构一样了。

代码写法上，四处要跟着变

有 .ui（原码） 纯代码（你这遍）
控件声明 在 .ui 里，代码里通过 ui->名字 访问 在 xxx.h 里当成员变量声明 QLabel *labelFirst;
控件创建 ui->setupUi(this) 一句搞定 在 xxx.cpp 里逐个 new
位置尺寸 在 .ui 里拖 控件->setGeometry(x, y, w, h)
布局 .ui 里拖布局 QHBoxLayout/QVBoxLayout + addWidget / addStretch
初始化入口 ui->setupUi(this) 自己写一个 void ui_init();，在构造函数里调

命名照抄原码：原码里叫 ui->labelFirst，你就把成员变量叫 labelFirst。这样对照原码时，把 ui-> 三个字符划掉就是你的代码。

⚠️ 最容易踩的坑：on_xxx_clicked() 会静默失效

这一条必须单独讲，因为它不报错、不警告，就是没反应 —— 最难查的一类 bug。

有 .ui 的时候，ui->setupUi(this) 内部会调用 QMetaObject::connectSlotsByName(this)。它的作用是按名字自动连信号槽：

// .ui 里有个按钮叫 pushButtonLeft，类里有个槽叫 on_pushButtonLeft_clicked
// → connectSlotsByName 自动帮你连上，你一个字都不用写
void banna::on_pushButtonLeft_clicked() { ... }     // 靠名字自动连上，函数体当然要你自己写
//  ↑ 函数名 = "on_" + 控件名 + "_" + 信号名，一个字符都不能差

没有 .ui 就没有 setupUi()，也就没人调 connectSlotsByName。 上面那个槽会变成一个永远不会被调用的普通函数 —— 编译通过、运行正常、点了没反应。

所以纯代码路线下，每一根连线都得手写：

// 纯代码路线：控件自己 new，信号槽自己 connect
void banna::ui_init()
{
    pushButtonLeft  = new QPushButton(this);     // 建控件；this 作父对象 → 自动进对象树、自动跟着窗口销毁
    pushButtonRight = new QPushButton(this);     // 再来一个
    // ...
    connect(pushButtonLeft,  SIGNAL(clicked()), this, SLOT(slot_leftClicked()));    // 左箭头 → 自己的槽
    connect(pushButtonRight, SIGNAL(clicked()), this, SLOT(slot_rightClicked()));   // 右箭头 → 自己的槽
    //      ↑ 全部显式连，不许偷懒用 on_xxx_clicked 自动连接（没有 .ui 就没有自动连接）
}

建议：把手写槽函数一律命名为 slot_xxx，不要用 on_xxx_clicked。 免得你以后某天加了个 .ui，同名的自动连接和手写 connect 同时生效，槽被执行两遍（附录 C 有这条）。 原码 banna.cpp 里用的正是 on_pushButtonLeft_clicked —— 那是因为它有 .ui，你照抄那个名字就会踩上面这个坑。

原码的 .ui 文件还是有用的

别删原项目那些 .ui。它们记录着真实的坐标和尺寸，是你写 setGeometry() 的唯一依据。 只是用法变了：不是拿来打开拖，而是当"尺寸清单"读。每个页面开头我都会把需要的坐标给你列成表。

顺带一提：少了一层间接，调试更好办

有 .ui 时你只能靠 qDebug() 或 ui->控件->text() 来查问题。 现在控件都是你自己 new 的、自己起的名字，断点能直接下在 ui_init() 里，一步步看着界面长出来 —— 这算是纯代码路线白送的好处。

⚠️ .pri 里行尾的反斜杠 \ 是续行符

—— 它表示"这一行还没完，下一行接着算"。所以：

  • 每加一行都要在行尾留 \，最后一行不能留（后面没东西了）。
  • 现在 HEADERS += \ 后面直接跟着空行，其实是空列表，qmake 能接受。
  • 忘了写 \ 的典型症状：新加的文件死活没被编译，或者报 undefined reference to 'Banna::Banna()' —— 因为 .cpp 根本没进构建。

    $$PWD/banna.h \
SOURCES += \          ← 接着上一行算，整段变成 "HEADERS += banna.h SOURCES +="
    $$PWD/banna.cpp \
# 正确写法：HEADERS 段和 SOURCES 段之间夹一个真正的空行，反斜杠才会在这里停住

    CreateInstanceFunc createInstance;          // 每一项自带"怎么造出这个页面"的办法

// 建界面：左边列表、右边页面堆栈，然后把两者连起来
void MainWidget::windows_init()
{
    hBoxLayout    = new QHBoxLayout();          // 横向布局；先当孤儿，setLayout 时才入树
    stackedWidget = new QStackedWidget();       // 右侧卡片盒：第 n 个 widget = 第 n 页
    listWidget    = new QListWidget(this);      // 左侧导航栏

    listWidget->setStyleSheet("background-color: black;");   // 导航栏底色涂黑

    // 全项目只有这个数组需要改：每完成一个页面，就往里加一行
    WidgetItemData items[] = {
        {"测试页A", []() -> QWidget * { return new QWidget; } },   // 空占位页；[] 不能捕获 → 才能当函数指针
        {"测试页B", []() -> QWidget * { return new QWidget; } },   // 同上
    };

    // 一趟循环同时喂两个容器：第 n 次迭代既加列表项、又加页面
    for (auto &itemData : items) {
        QListWidgetItem *item = new QListWidgetItem(itemData.title);   // 造一个列表项
        item->setTextColor(Qt::white);                                // 白字（5.15 会警告 deprecated，无视）
        item->setTextAlignment(Qt::AlignCenter);                      // 文字居中
        item->setSizeHint(QSize(200, 63));                            // 每一项 200 宽 × 63 高
        listWidget->addItem(item);                                    // 塞进导航栏

        if (itemData.createInstance)                                  // 有造页面的函数才加
            stackedWidget->addWidget(itemData.createInstance());      // 造一个页面塞进堆栈
    }

    listWidget->setMaximumWidth(200);           // 导航栏最宽 200px（剩下 824 给页面）
    hBoxLayout->addWidget(listWidget);          // 左边：导航栏
    hBoxLayout->addWidget(stackedWidget);       // 右边：页面堆栈
    widget->setLayout(hBoxLayout);              // 布局挂到容器上（这一句之后控件才听布局的）

    connect(listWidget, SIGNAL(currentRowChanged(int)),      // 列表"当前行变了"
            stackedWidget, SLOT(setCurrentIndex(int)));       // ★ 全部切换逻辑就在这一行
}

三个必须想明白的点（这就是第 0 级的验收）：

  1. 为什么 lambda 的捕获列表必须是空的 []？ 因为 C++ 规定只有不捕获任何变量的 lambda 才能隐式转换成普通函数指针，而这里要赋给 createInstance。写成 [this] 直接编译错误。

  2. 为什么 stackedWidget 的索引能和 listWidget 的行号直接对应？ 因为 for 循环里第 n 次迭代，既 addItem 了第 n 个列表项，又 addWidget 了第 n 个页面 —— 两个容器的顺序天然一一对应，所以 currentRowChanged(int) 可以直接喂给 setCurrentIndex(int)，不需要任何映射表。

  3. 原项目的 setCurrentItem() 为什么要搬到 connect 后面？ 原码里 setCurrentItem(item1) 写在 connect 之前，它发射的 currentRowChanged(0) 根本没人在听，信号被丢掉了。程序之所以还能显示第 0 页，纯属 QStackedWidget 加第一个控件时默认 currentIndex = 0 兜底。 信号槽是运行时机制，连接之前发出的信号不会补发。 正确写法是把设焦点的代码块搬到 connect 之后。

编译时会蹦一个 setTextColor is deprecated 警告 —— 不用管它。 Qt 5.15 建议改用 setForeground()，但原码用的是 setTextColor()，板子上是 Qt 5.12 也不报这个警告。看到 warning 不看到 error 就是成功，别去"修"它 —— 现在改就和原码对不上了。等你把这一级写完对照原码时，会发现作者也这么写。

class SwitchButton : public QWidget {                     // 自绘控件：外观全靠自己画，不用任何现成控件
    Q_OBJECT                                              // 下面有 signals: → 必须有 Q_OBJECT
public:
    explicit SwitchButton(QWidget *parent = nullptr);     // 构造函数；画的事不在这做，在 paintEvent
    bool isChecked() const { return m_checked; }          // 读状态：给外面查询用（const = 不改成员）
    void setChecked(bool c) {                             // 写状态：代码路径设开关，不走"用户点击"那条路
        m_checked = c;                                    // 先改成员变量
        update();                                         // 再请求重绘 —— 故意不发 toggled 信号（防死循环）
    }
signals:
    void toggled(bool);                                   // 状态翻转时发出去（只有用户点出来才发）
protected:
    void paintEvent(QPaintEvent *) override;              // 所有绘制都在这里：画轨道 + 画滑块
    void mouseReleaseEvent(QMouseEvent *) override;       // 鼠标松开 = 一次点击 → 翻转状态
private:
    bool m_checked = false;                               // 开关状态；m_ 前缀是成员变量的通行写法
};

paintEvent 里只画两样：圆角矩形轨道（QPainterPath + addRoundedRect + drawPath）和圆形滑块（drawEllipse）。滑块中心 x 按 m_checked 在左端/右端之间取。

mouseReleaseEvent 里取反 + emit toggled(m_checked) + update()。

// ↑ 能这样按名字写 "deviation" 的前提：NumberPicker 里声明了

//   没有这个宏，QPropertyAnimation 找不到属性，动画不动也不报错。

QString findIioDevice() {                                    // 返回形如 /sys/bus/iio/devices/iio:device1
    QDir dir("/sys/bus/iio/devices/");                       // 打开 IIO 设备目录
    for (const QString &dev : dir.entryList(QDir::Dirs | QDir::NoDotAndDotDot)) {   // 只列子目录，跳过 . / ..
        QFile f("/sys/bus/iio/devices/" + dev + "/name");    // 每个设备目录下都有一个 name 文件
        if (f.open(QIODevice::ReadOnly) && f.readAll().trimmed() == "icm20608")     // 读出来比一比
            return "/sys/bus/iio/devices/" + dev;            // 命中 → 就是它
    }
    return QString();                                        // 没找到 → 返回空串，调用方必须判空
}

float readSysfsFloat(const QString &path) {                  // 读一个 sysfs 文本文件并转成 float
    QFile f(path);                                           // QFile 是 Qt 对文件描述符的封装
    if (!f.open(QIODevice::ReadOnly)) return 0.0f;           // 打不开就当 0，别让程序崩（防御性写法）
    return f.readAll().trimmed().toFloat();                  // 全读出来 → 去掉换行 → 转浮点
}

4.3 Step 2 — 再写 AP3216C（I2C，稍难）

📁 放哪：

hardware/ap3216c.h + hardware/ap3216c.cpp（新建），同样补进 hardware/hardware.pri

这条路是用户态直接操作 I2C 总线，不走内核驱动：

fd = open("/dev/i2c-0", O_RDWR);              // ① 打开总线（/dev/i2c-0 通常要 root 权限）
ioctl(fd, I2C_SLAVE, 0x1E);                   // ② 声明要跟哪个从机说话：0x1E 是 AP3216C 的地址

// ③ 写寄存器：一次 write 两个字节 {寄存器地址, 值}
uint8_t buf[2] = {reg, val};                  // 第一个字节 = 寄存器号，第二个字节 = 要写的值
write(fd, buf, 2);                            // I2C 写寄存器就是这么"发两个字节"

// ④ 读寄存器：先写寄存器地址，再读一个字节
write(fd, &reg, 1);                           // 先告诉从机"我要读哪个寄存器"
read(fd, val, 1);                             // 再把那个寄存器的值读回来

初始化流程： 写 0x00 = 0x04（软复位）→ usleep(15000) → 写 0x00 = 0x03（ALS+PS+IR 全部开启）。

数据解析（位运算，容易写错）：

量 位数 公式
IR 14 位 (high << 2) \| (low & 0x03)，low & 0x80 是无效标志
PS 10 位 ((high & 0x3F) << 4) \| (low & 0x0F)，low & 0x40 是无效标志
ALS 16 位 (high << 8) \| low

验收：用手电筒照传感器，ALS 数字明显变大；手靠近，PS 明显变化。

void imx6ullTest::setLedState()                       // 点一次 LED 按钮就进来一次
{
    if (!file.exists()) return;                       // 防御：节点不存在就直接退出（本板就走这一行）

    file.open(QIODevice::ReadWrite);                  // 以读写方式打开
    QByteArray data = file.readAll();                 // 先读当前值
    file.seek(0);                                     // 文件指针拨回开头，否则写会追加到末尾
    file.write(data.contains('0') ? "1" : "0");       // 写反值 = 翻转（现在是 0 就写 1）
    file.flush();                                     // 立刻刷出去，别攒在缓冲区里
    file.close();                                     // 关上
}

getLedState() 就是"读出来看是不是 1"，然后更新按钮上的文字。

🔧 在你这块 100ask IMX6ULL 上：

/sys/class/leds/ 里只有 mmc0:: 和 mmc1::（eMMC/SD 卡的活动指示灯），没有 sys-led，也没有 beep。 所以这段代码在这块板上不会亮灯，但也不会崩 —— 它会走到 !file.exists() 那行直接 return，界面上显示"未获取到LED设备！"。

照写，并且在代码里加上注释：

// 🔧 本板(100ask IMX6ULL)无 sys-led / beep 节点，此功能在本板不可验证；
//    本板 /sys/class/leds/ 下只有 mmc0:: 和 mmc1::
//    在正点原子 ATK IMX6U 上 /sys/class/leds/sys-led/ 存在，可直接验证。
//    本板行为：exists() 返回 false → 函数直接 return，界面显示"未获取到LED设备！"
file.setFileName("/sys/devices/platform/leds/leds/sys-led/brightness");   // 让 QFile 盯住这个节点

为什么仍然要完整写？三个理由：

  1. 这是嵌入式 Linux 用户态控制硬件最常见的方式（sysfs 一个字符搞定），必须会；
  2. exists() 守卫 + "未获取到设备"提示是教科书级的防御性编程 —— 硬件可能不存在、可能没权限、可能被别的驱动占着，你的程序都不该崩；
  3. 它演示了「同一个程序换一块板子行为就不同」—— 这正是你现在面对的处境，早认清早主动。

想在本板上真的点个灯（课外扩展）： 用 /sys/class/gpio/（echo <N> > export → echo out > direction → echo 1 > value），或者去改 mmc0:: 的 trigger 文件。不影响主线。

5.6 ⚠️ 三个必须避开的坑

① 进度条死循环。 positionChanged → 更新 slider 位置；sliderReleased → setPosition()。 如果顺手把 slider.valueChanged 也连到 setPosition，两者会互相触发，进度条疯狂抖动。 原码的解法：positionChanged 里只在 !isSliderDown() 时才更新 slider，并且不连 valueChanged。

② 列表点击与索引同步。 itemClicked → stop() + setCurrentIndex(row) + play()；currentIndexChanged → setCurrentRow(index)。 之所以不成环，是因为 setCurrentRow() 不会触发 itemClicked。 如果你换成 itemSelectionChanged 或 currentRowChanged，立刻死循环。

③ 找不到文件不报错。 目录不存在时 scanSongs() 只打一行 qDebug，界面上列表就是空的，什么提示都没有。 这是新手最容易卡住的地方 —— 先怀疑路径，再看代码。

⚠️ Mat → QImage 的正确写法（本级的核心技术点）：

QImage matToQImage(const cv::Mat &mat)              // 本级核心：cv::Mat → QImage
{
    if (mat.type() == CV_8UC3) {                    // 只处理 8 位 3 通道 —— 摄像头抓出来的正是这种
        QImage img(mat.data, mat.cols, mat.rows, mat.step,         // ← 第 4 个参数必须是 mat.step，不是 cols*3
                   QImage::Format_RGB888);          // 像素格式：每像素 3 字节，顺序 R,G,B
        return img.rgbSwapped();                    // ← BGR→RGB，并且顺带复制出一份新数据（见下面第 2 点）
    }
    // CV_8UC4 用 Format_ARGB32 + copy()
    return QImage();                                // 其它格式返回空图，调用方自己判 isNull()
}

三个细节，缺一个就花屏：

  1. 第 4 个参数必须是 mat.step，不是 cols * channels()。 Mat 每行可能有对齐填充（padding），宽度不是 4 的倍数时用后者会错位。

    原项目的 opencv.cpp 里大部分地方写错了（只有极少数位置用对了），而 camera.cpp 写对了。以 camera.cpp 为准。

  2. rgbSwapped() 做了两件事：把 BGR 转成 RGB，并且返回一份新数据。这顺带解决了"QImage 只是包了 Mat 的内存、不持有所有权，Mat 析构后指针悬空"的问题。
  3. 如果用 Format_Indexed8 显示灰度图，必须设 colorTable，否则显示异常。

验收：QLabel 里出现摄像头实时画面。

⚠️ setObjectName() 那一行是干什么的？

你后面要给这 40 个按钮连槽。写成显式的 40 句 connect 当然可以，但更漂亮的做法是在同一个循环里连：

// Qt5 新式写法（指向成员函数的指针），可以放进循环里用变量
connect(b, &QPushButton::clicked, this, &opencv::slot_dispatch);   // b 是循环变量 —— 字符串写法做不到这一点
// 然后在 slot_dispatch() 里用 sender()->objectName() 分发到对应算子

这是本手册第一次出现 Qt5 新式 connect。 前面全程用的 SIGNAL()/SLOT() 字符串写法，好处是跟原码一致、能逐行对照，坏处是槽名必须是编译期字面量，进不了循环。 40 个按钮是唯一值得破例的地方。两个写法在 Qt5 里完全可以混用，同一份代码里两种并存不会打架。 （如果 dispatch 那一层你觉得绕，那就老老实实敲 40 句 connect(b, SIGNAL(clicked()), this, SLOT(xxx())); —— 也没错，只是长。）

8.1 MQTT 页面 —— 先解决库的问题

这是整个项目部署上最麻烦的一环。 板子自带 /usr/lib/libQt5Mqtt.so.5 指向的是 Qt 5.12.9 编译的版本，而你的程序是 5.12.8 —— 一启动就崩：

# 板子上启动时的报错原文（库版本对不上，程序直接 abort —— 不是警告）
Cannot mix incompatible Qt library (version 0x50c09) with this library (version 0x50c08)
#     0x50c09 = 5.12.9（板子自带的 libQt5Mqtt.so.5）   0x50c08 = 5.12.8（你的程序）

而且因为 windows_init() 是立即构造全部页面的（见 mainwidget.cpp），MQTT 库坏掉会导致整个程序启动就 abort，哪怕你根本不打算用 MQTT。

🔧 这是全项目唯一一个"必须先解决环境问题才能往下走"的地方 —— 也是最有价值的一课。

主线做法：用源码把库重新编出来。

原项目里带着完整的 QtMqtt 源码：project/lib/arm_qtmqtt/src/mqtt/。 但你不能直接 qmake 它 —— 它的 mqtt.pro 结尾是 load(qt_module)，那是 Qt 官方模块才有的写法，会报 Module does not define version。

正确做法是把它当成一个普通共享库来编：

QT       += core network core-private   # core-private 必须加：QtMqtt 源码里 include 了 <private/qobject_p.h>
TEMPLATE  = lib                         # 不是 app，是"编一个库"
TARGET    = Qt5Mqtt                     # 目标名 → 生成 libQt5Mqtt.so
VERSION   = 5.12.8                      # 版本号，决定后面 .so.5 / .so.5.12 那串符号链接叫什么
SOURCES  += .../src/mqtt/*.cpp          # 原项目带的 QtMqtt 源码（... 换成你机器上的实际路径）
HEADERS  += .../src/mqtt/*.h            # 头文件同上

# 用板子的交叉 qmake 编（⚠️ 不是主机的 qmake）
/home/book/100ask_imx6ull-sdk/Buildroot_2020.02.x/output/host/bin/qmake qtmqtt_arm.pro   # 生成 Makefile
make -j$(nproc)                                    # 编译，-j$(nproc) = 把 CPU 核全用上
adb push libQt5Mqtt.so.5.12.8 /usr/lib/            # 推到板子的系统库目录
# 把 .so / .so.5 / .so.5.12 三个符号链接都指向它（ln -sf libQt5Mqtt.so.5.12.8 xxx）

现成的可参考工程：smart_terminal-main/build-qtmqtt-arm/qtmqtt_arm.pro。 这么编出来约 226 KB，而板子原来那个是 4.7 MB（带了调试信息）。程序启动时会打一行 no version information available 警告 —— 无害。

这一课学到的东西，比 MQTT 本身值钱：

  • Qt 的库版本校验机制（为什么"混用"会直接 abort 而不是弹个警告）
  • 交叉编译一个第三方库的完整流程（从源码到 push 到符号链接）
  • .so 版本号与符号链接的管理

这是全项目最底层的一块：不通过 OpenCV，直接用 ioctl 操作摄像头。

run() 里的 V4L2 标准流程（背下来，这是通用知识）：

# V4L2 取流的标准流程（通用知识，值得背下来；这不是要敲的代码，是 run() 里的步骤）
open("/dev/video1", O_RDWR)                     # ① 以读写方式打开摄像头设备
  → ioctl(VIDIOC_S_FMT)      设置格式 640×480 / V4L2_PIX_FMT_RGB565    # ② 定格式（⚠️ 坑①：USB 摄像头多半不支持，见正文）
  → ioctl(VIDIOC_REQBUFS)    申请 3 个 mmap 缓冲                        # ③ 向驱动申请 3 个缓冲
  → 对每个缓冲 QUERYBUF + mmap 映射到用户空间                           # ④ 先问内核这块多大，再映射进你的地址空间
  → 对每个缓冲 QBUF 入队                                               # ⑤ 把 3 个缓冲全交给驱动去填
  → ioctl(VIDIOC_STREAMON)   开始采集                                  # ⑥ 开流，从这一刻起才有帧
  → while (startFlag) {                                              # ⑦ 一直循环，直到 startFlag 被置 false
         ioctl(VIDIOC_DQBUF)   取出一帧                                #    出队一帧（拿到的是一条缓冲的编号）
         ... 用 mmap 地址构造 QImage 显示 / 编码广播 ...                #    ⚠️ 坑②：这里必须 .copy()，否则画面花屏
         ioctl(VIDIOC_QBUF)    还回队列                                #    还回去，否则驱动再也不会给你新帧
    }
  → STREAMON 关闭 + munmap + close                                    # ⑧ 收尾：关流 → 解除映射 → 关设备

⚠️ 四个坑，一个一个说。

① 原码用 V4L2_PIX_FMT_RGB565

USB 摄像头通常不支持这个格式，S_FMT 会静默失败然后直接 return，表现为"程序没反应但也不报错"。复现时先查：

adb shell "v4l2-ctl -d /dev/video1 --list-formats"   # 先查摄像头支持哪些像素格式 —— 别照着原码瞎设格式

真要用 USB 摄像头，多半得改成 V4L2_PIX_FMT_YUYV 或 MJPEG，再自己转码。

② QImage 直接包装 mmap 内存、没有 .copy()，下一行就把缓冲还回队列了

显示端一旦排队延迟，画面就会花屏。这是真 bug，你必须加 .copy()。

③ quit() 对没有事件循环的线程没用

CaptureThread::run() 里没有 exec()，所以 setThreadStart(false) 调用的 quit() 什么也不做 —— 真正让它退出的是 startFlag 变成 false。

④ 只在 __arm__ 下有效

run() 开头有 #ifndef __arm__ return;，所以 PC 上测这个页面永远是黑屏，这是预期行为不是 bug。

UDP 广播怎么发的：

QByteArray buf;                                                  // 装 JPEG 字节
qImage.save(&buff, "JPEG", -1);                                  // 编成 JPEG（-1 = 默认质量）—— 注意这里传的是 &buff
QByteArray data = buff.toBase64();                               // 再转 base64，好塞进纯文本的 UDP 报文
udpSocket->writeDatagram(data, QHostAddress::Broadcast, 8888);   // 广播出去（⚠️ 超过 65507 字节会返回 -1，原码不检查）

目标地址是广播地址 255.255.255.255 + 端口 8888，写死在代码里。

⚠️ 单包上限 65507 字节，base64 还会再膨胀 33%。

640×480 的 JPEG 经常超限，writeDatagram 返回 -1 但代码不检查 → 整帧静默丢弃。真要稳，得自己做分片。

    checkBox1->move(this->width() - 120, this->height() / 2 - 50);              // 复选框贴右边、竖直中线偏上 50px
    checkBox2->move(this->width() - 120, this->height() / 2 + 25);              // 另一个在它下方 75px 处
}

用相对算式摆位置，而不是写死数字，也不是丢给布局 —— 窗口一变大变小，画面自动居中、按钮自动贴底、复选框自动贴右边。三种方法各有各的用场：

方法 什么时候用 本手册哪里
setGeometry(固定数字) 动画要改 geometry，布局会捣乱 第 1 级 banna
布局管理器 排一系列同类控件，尺寸不定 第 4/5/6 级
resizeEvent 里算 全屏画面、边角按钮，要"跟着窗口走" 就是这一页

为什么要重写 resizeEvent 而不是在构造函数里算一次？ 因为构造函数只跑一次。 你把窗口拉大了，width() 已经变了，但没人通知那些控件 —— 除非你在这个"窗口尺寸变了"的回调里重新摆一遍。 和 paintEvent 一样，这是重写 Qt 提供的"事件回调"（第 2 级你重写过 paintEvent / mouseReleaseEvent）：框架在该调用的时候调你，你只管填内容。

A.3 触摸又失灵了？（第二层原因）

即使环境变量对，触摸还可能再次失效。那是另一个独立的原因：goodix-ts 驱动的 I2C 读挂了。

先确诊（tslib 会独占设备，先 kill 掉你的程序）：

adb shell "timeout 40 cat /dev/input/event1"     # 手按屏幕按满 40 秒；一个字节都没有 = 内核根本没产生事件
adb shell "dmesg | grep goodix-ts | tail -5"     # 看驱动日志里有没有 I2C transfer error. errno:-11

0 字节 + I2C 报错 = 确诊，就是驱动问题，不要去改 Qt 配置。 （如果怀疑是 Qt 那层，用这个和 A.2 那段环境变量互相排除。）

修复 —— 强制驱动重新探测（驱动是编进内核的，没有模块可以 reload）：

adb shell "echo 1-005d > /sys/bus/i2c/drivers/goodix-ts/unbind"   # 把驱动从 1 号 I2C 总线上的 0x5d 设备解绑
sleep 1                                                            # 等一秒，让驱动彻底松手
adb shell "echo 1-005d > /sys/bus/i2c/drivers/goodix-ts/bind"     # 再绑回去 = 强制重新探测（驱动编进内核了，没有模块可 reload）

设备会重新注册，/dev/input/event1 被重建，然后重新启动程序。

悬而未决： 触发原因不明，也不确定重启板子后会不会复发。 一个未被证实的猜测：音频播放器打开 wm8960（和触摸控制器共用 i2c-1，也是 HDMI 的 sii902x 所在总线）时把总线搞挂了。 如果触摸又死了，先看 dmesg，别先动 Qt 配置。

//    - 原因：/sys/class/leds/ 下只有 mmc0:: 和 mmc1::，没有 sys-led / beep 节点
//    - 本板可用节点：mmc0:: / mmc1:
//    - 可在正点原子 ATK IMX6U 上验证（该板 /sys/class/leds/sys-led/ 存在）
//    - 本板行为：exists() 返回 false，函数直接 return，界面显示"未获取到设备"
file.setFileName("/sys/devices/platform/leds/leds/sys-led/brightness");   // 让 QFile 盯住这个节点（本板上它不存在，所以上面得写清楚）

写这种注释本身就是一项能力 —— 换个人接手、或者半年后的你自己回来看，一眼就知道这段为什么"没效果"。

你已经能改掉的原码问题

复现不等于照抄。下面这六处是原码的已知问题，每一处都标了改法，改掉它们才算真的读懂了：

  1. 轮播图里那些 new 出来却没设 parent 的 QPropertyAnimation（内存泄漏）
  2. 图表 Y 轴写死 40，而 ALS 能到 65535（量程）
  3. 数据库用相对路径 "alarm.db"（换个目录就"丢数据"）
  4. 闹钟删行后不更新 itemObjectInfo（索引漂移，会写错行）
  5. CaptureThread 里 QImage 包装 mmap 内存没 copy()（花屏）
  6. 闹钟到点不会响 —— 加个 QTimer 就能把三个级别串起来

把这六个改掉，这个项目就真正是你的了。

还有第七条，是你从第一行代码起就在做的

原项目 9 个页面有 7 个是 Designer 拖出来的 —— 拖的时候你不知道 setGeometry 是谁调的、connectSlotsByName 什么时候生效、qss 是怎么套上去的。

你这遍把它们全部手写了一遍。 所以回头看原码那些 .ui，你能读出别人读不出来的东西：

  • 一个控件在 .ui 里的 geometry，等价于哪一行 setGeometry；
  • 为什么 banna 必须手摆坐标、imx6ulltest 必须用布局；
  • ui->labelThird->raise() 里的 ui-> 到底省掉了什么；
  • 那个把 clicked 执行两遍的"自动连接"，机制上是怎么来的。

这就是为什么手册一开始就要求不用 Designer。 会拖控件的人很多，知道自己拖完以后编译器替你生成了什么代码的人，很少。
